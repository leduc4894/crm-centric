# Contact upsert SDK migration

ADR-020 changes `POST /api/v1/contacts`: a new contact returns `201`; an existing active email returns `200` only with a matching strong `If-Match` and expected `X-Contact-Id` UUID. Both identify the same current active contact. A missing precondition returns `428`, stale returns `412`, and malformed values return `400`. A matching no-op preserves its version and ETag. The server implementation and deployment are separate work; this document does not claim either has shipped.

This is a source and behavior break. The historical .NET `Crm.Client` package is version `1.0.0`; the generated candidate is `2.0.0`. The historical TypeScript `@crm-centric/crm-client` version is `0.1.0`; the candidate is `0.2.0`. They are independent version lines; do not replace a package with different content under the same version. No package has been published by this change.

Before enabling the server change, update and deploy consumers that may POST an existing email:

1. Pin the new package version and regenerate the consumer's own lock through its normal package review; do not modify the historical fixture lock or trusted contract baseline.
2. Handle both `201` and `200`, read the returned contact ID and strong ETag together, and send both as `X-Contact-Id` and `If-Match` for a subsequent update. If an existing email needs updating and no current ETag is available, obtain the contact and ETag through an authorized existing lookup workflow; the POST must not silently overwrite on `428` or `412`. Recovery and user confirmation behavior depend on the consumer.
3. Handle `400`, `412` and `428` Problem responses; preserve user input on a conflict and refresh before retry. Omitted optional fields are retained on update; explicit null clears nullable fields. A submitted display name is required and replaces the current value.
4. For generated .NET, `CreateContactResponse.ETagHeader` changes from `PostApiV1ContactsCreatedETag` to `PostApiV1ContactsOkETag`; `MatchResult` adds handlers for `200`, `412` and `428`. Update typed assignments and exhaustive match handlers. The generated POST method also adds the optional `ifMatch` argument before cancellation/validation arguments; audit positional calls and prefer named arguments. The TypeScript response union and optional request headers change as well. ADR-021 adds `xContactId` to generated .NET POST calls; review named and positional arguments. This candidate package version has not been published and its test fixture locks are refreshed for the new contract; never replace a published package under the same version.
5. Validate the migrated consumer against the target environment and keep the older server/SDK artifact available for rollback. Roll back consumer and server as a coordinated pair: a v1 consumer may treat a v2 server's `200` response as an error. Do not send upserts while operating a 201-only client.

`tests/ClientConsumers/contact-upsert/run.sh` packages the pre-upsert source from immutable revision `db04aea` as 1.0.0 and the current candidate as 2.0.0, restores separately pinned fixture consumers, and exercises generated SDK request/response handling with an in-process HTTP handler. It also checks that the old consumer source fails to compile against v2. This is bounded fixture evidence, not an external production consumer, compatibility approval, or a trusted baseline advancement. The existing historical lock in `tests/ClientConsumers/dotnet/` remains unchanged. Existing repository compatibility and packaged-consumer gates must still be addressed under their established governance before release.
