# Contact foundation migration

`20261127000000_ContactFoundation` adds tenant-scoped contacts, a durable event-intent table and an audit append function. Run the existing migrator with its separate migration and application roles; it checks role boundaries before and after migration. The CRM and outbox tables use raw SQL migrations rather than EF entities. Future schema changes must account for those objects explicitly.

The down migration is permitted only when there are no contacts, contact intents, or contact audit entries. It checks each tenant under forced RLS and aborts the transaction if it finds data. When data exists, take and verify a backup and create a reviewed forward migration; do not delete records merely to force a downgrade. A restore and recovery drill remains a separate acceptance requirement.

The outbox stores contact mutation intent in the same transaction as the business write and audit. It does not implement delivery or a consumer.

`20261127010000_ContactEmailUpsert` adds a generated `email_normalized` using PostgreSQL `lower(btrim(email))` and a partial unique index for active contacts with an email, scoped by tenant. It takes an exclusive contact-table lock and checks every tenant before building the index. If active normalized duplicates exist, the migration aborts transactionally with `CONTACT_EMAIL_DUPLICATES` and does not print email addresses or select a winner. An authorized operator must investigate and reconcile duplicates using a controlled process, then rerun migration; preserve audit and outbox records. PostgreSQL's default `btrim` removes ordinary spaces and `lower` follows the database collation. Querying code should use the same database expression, not a separate application normalization.

Reverting this migration is allowed only while the contact table is empty; with any contacts, take and verify a backup and use a reviewed forward fix. Consumer migration and rollback are described in ADR-020; this migration does not by itself establish consumer readiness or compatibility.

The API preserves the submitted email's case after trimming ordinary surrounding spaces; uniqueness and lookup use the generated database expression above. Contact UUID remains stable across an email upsert. An existing active match requires a current strong ETag and matching `X-Contact-Id`; a complete valid pair without an active match returns 412. Sending only one precondition returns 428. Deleting a contact or clearing its email releases the active unique key. These semantics are contract changes and require the [SDK consumer migration](07-CONTACT-SDK-MIGRATION.md) before rollout. Never treat a successful local migration or fixture consumer as proof that existing production data or consumers are ready.

`20261127020000_ContactTagsFoundation` adds tenant-scoped tags and contact-tag links with composite tenant-aware foreign keys, forced RLS, and read-only application grants. Plan 3 owns tag mutation APIs and must add authorization, auditing and concurrency controls. Rollback locks both tables and fails closed if either contains data; take and verify a backup and use a reviewed forward fix rather than deleting records to force rollback. See the [query-plan evidence](../engineering/14-WAVE-2-CONTACT-LIST-QUERY-PLAN.md) for the existing read indexes; this is not a performance exit benchmark.
