## Generator selection and prerequisites

The two canonical OpenAPI 3.1 documents generate TypeScript types using openapi-typescript 7.13.0, with openapi-fetch 0.17.0 as transport, and C# clients using Corvus.Json.Cli 5.8.8. The CLI NuGet artifact SHA-256 is `b023226e7cffe4b58578ed51c460424cfadfbfe4b223abae020b6e5960a68051`; .NET build/runtime dependencies have NuGet locks. The pinned .NET SDK image digest and all selected versions are in `tools/contracts/toolchain.json`; Node/npm are pinned in `.node-version` and `package.json`. Generated code is local only; it is not evidence of implemented business routes or server validation.

The initial OpenAPI Generator 7.27.0 TypeScript Fetch and Generic Host C# candidates produced code that lost valid action fields. Its RestSharp C# template could round-trip individual actions but rejected valid recursive conditions and exposed payloads in diagnostics. NSwag 14.7.1 failed to compile the actual CRM contract; Kiota 1.38.0 generated an action union whose factory did not populate its member. Those experiments did not establish that other versions or configurations cannot work.

Install the exact Node/npm versions, Docker, and Python contract dependencies. Populate npm's cache using `npm ci --ignore-scripts`, then place the official `corvus.json.cli.5.8.8.nupkg` under `.local/plan3-tools/`; `generate.py` verifies its SHA-256 before extraction and executes the generator in a network-isolated pinned container. Retrieve the artifact from the NuGet flat-container endpoint `https://api.nuget.org/v3-flatcontainer/corvus.json.cli/5.8.8/corvus.json.cli.5.8.8.nupkg`. The package is not committed. Generation installs locked npm dependencies into an isolated temporary directory with `npm ci --offline --ignore-scripts` and does not execute npm lifecycle scripts. `check.py` regenerates in a temporary directory and compares full generated trees without writing generated content into the workspace.

The Corvus lock file's `generatedAt` field is removed and generated C# line endings are normalized to LF before comparison; all other generated bytes are retained. Provenance in each output records per-file hashes for the validated transitive local input closure, plus generator artifact and configuration hashes. These are local checks, not a claim about published packages or remote CI.

### Task 4 SDK surface and toolchain gate (review pending)

The compatibility gate regenerates both sides of the comparison in isolated temporary roots. When the resolved Git base already contains `tools/contracts/toolchain.json`, the base SDK is produced with the base's own generator, configuration and pinned .NET image and the candidate SDK with the current worktree's; a first bootstrap uses the selected current toolchain for both sides and reports `bootstrap-no-released-consumer`. The gate compares TypeScript exported declarations (removed, renamed, retyped or nullability-changed members) and compiled .NET public API (types, members, nullability) and compiles the Git-base TypeScript and C# consumer fixtures against the candidate SDKs. `sdkBaseline`, `sdkToolchain` and `sdkToolchainChanged` identify the baseline kind and the generator/configuration hashes of each side. Missing or unusable historical toolchains, missing historical consumer artifacts and tool errors fail closed as `SDK_TOOLCHAIN_REVIEW_REQUIRED`; an incompatible surface is `SDK_SURFACE_INCOMPATIBLE` with classification `SDK-surface-incompatible`. A candidate edit to an existing comparison policy or waiver file, or a new such file, is `CONTRACT_POLICY_REVIEW_REQUIRED`. The gate writes no generated output, baseline or waiver into the worktree, never fetches, resets or rebases Git, and prints only hashes, reasons and correlation IDs.

### Task 5 frontend workspace and restricted local proxy (review pending)

The repository root is now an npm workspace root. `package.json` declares `workspaces: ["apps/crm-web", "sdks/typescript/*"]`, pins `packageManager` to npm 11.19.1 and delegates the `dev`, `build`, `typecheck`, `lint` and `test` scripts to `@crm-centric/crm-web`. `package-lock.json` is committed and `npm ci` from the repository root installs the whole workspace from that lockfile. `apps/crm-web` is a React 19.3.1 + TypeScript 5.9.3 + Vite 8.3.7 application with strict TypeScript (`strict`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `verbatimModuleSyntax`, `isolatedModules`, `skipLibCheck: false`).

Selected versions, each resolved from the npm registry and pinned exactly (`.npmrc` sets `save-exact=true`): react 19.3.1, react-dom 19.3.1, vite 8.3.7, @vitejs/plugin-react 6.3.0, vitest 5.1.0, typescript 5.9.3, eslint 10.14.0, @eslint/js 10.0.1, typescript-eslint 8.72.2, eslint-plugin-react-hooks 7.1.1, globals 17.14.0, @types/react 19.3.0, @types/react-dom 19.3.0, @types/node 24.19.2, openapi-fetch 0.17.0, openapi-typescript 7.13.0, npm 11.19.1, Node 24.22.2. No router, query library, form library, chart/editor or component catalog was installed because this slice has no consumer for them.

The dev server binds `localhost:5173` with `strictPort: true`. The proxy allowlist is the two operational paths `/health/live` and `/health/ready`, expressed as a single regular-expression proxy key derived from the allowlist so the two cannot drift apart, and forwarded to `http://127.0.0.1:${LOCAL_API_PORT:-5080}` with `changeOrigin: false`. `LOCAL_API_HOST` is accepted but restricted to the loopback literals `127.0.0.1` and `::1`. A malformed port fails with `WEB_PROXY_TARGET_INVALID` and a non-loopback host with `WEB_PROXY_TARGET_NOT_LOOPBACK`, both carrying a correlation ID and both raised before any server starts. The allowlist is validated at startup and rejects the empty list, the root path, relative paths, wildcards, query fragments, trailing slashes and duplicates with `WEB_PROXY_PATH_INVALID`. No wildcard CORS origin is configured and the identity provider, admin API and business API are never proxied. The whole environment is never loaded into the browser bundle: only the dev-server-side proxy target is read, and the production bundle contains no environment variable, secret or credential.

The `HealthClient` is a thin adapter over the generated `@crm-centric/operations-client`. It uses the generated `createApiClient`, keeps requests same-origin, adds no authorization, cookie or tenant header, stores no token and writes nothing to browser storage. The generated client already sets `credentials: 'omit'`. The adapter validates the server reason token and correlation ID before exposing them and falls back to the local classification `WEB_HEALTH_UNAVAILABLE` when the server sends no usable reason token. A transport failure is not swallowed: it propagates to the caller, because the closed error paths of this slice are the HTTP Problem responses.

The frontend consumes the generated operations client from its generated TypeScript entry point through a Vite alias and a TypeScript path mapping. The generated package's published entry point is the compiled `dist/` output, which is an uncommitted build artifact, so resolving to the generated source keeps the frontend on the generated public surface without writing build output into the byte-compared `sdks/` tree.
