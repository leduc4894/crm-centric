### Task 5 fix round 1 — credential stripping and matcher escaping (review pending)

The independent review of `ffcc7ae` raised one blocking Important finding and one recommended finding, both in the proxy boundary.

**I-1 — the dev proxy relayed the browser's credential headers to the upstream API.** http-proxy copies the incoming request headers into the outgoing request (`outgoing.headers = { ...req.headers }`) and deletes `authorization` only when `options.auth` is set, which the health proxy does not set. A loopback stub therefore received `authorization: Bearer …`, `cookie: session=…` and `x-tenant-id: …` from the browser. The operational endpoints are anonymous by contract, so relaying them would hand a browser session or a tenant selection to the API host the moment the browser holds credentials.

The fix removes the credential-bearing headers at the proxy boundary, in the proxy's own request hook, so it applies to every proxied request:

- `apps/crm-web/config/healthProxy.ts` adds `STRIPPED_PROXY_HEADERS = ['authorization', 'cookie', 'x-tenant-id']` and a `configure` hook on the proxy options that removes them in the `proxyReq` event.
- `authorization` is the `bearerAuth` scheme of the CRM API contract; `cookie` is the browser session; `x-tenant-id` is the canonical tenant context header of the CRM API (`docs/contracts/crm-api.openapi.yaml`, the `TenantContext` parameter). No invented tenant header name was added.
- The list is deliberately small. `Accept`, `Content-Type` and `X-Correlation-Id` are legitimate request headers and are forwarded unchanged, and the regression test asserts that they still arrive.

**M-4 — the proxy matcher was only incidentally regex-safe.** The matcher was built by joining the allowlist paths with `|`, so a future path such as `/health/live.v2` would have produced a matcher that also accepted `/health/liveXv2`. `buildProxyMatcher` now escapes every regular-expression metacharacter of every path, so the "the allowlist and the matcher cannot drift apart" guarantee is structural rather than incidental.

Covering tests:

- `apps/crm-web/config/devServer.test.ts` — `never relays a credential-bearing header to the upstream API`: the real Vite dev server plus a real loopback stub API. The stub now records the headers it received. The request carries `authorization`, `cookie` and `x-tenant-id`; the assertions require the upstream to have received none of them, and to have received `accept` and `x-correlation-id`.
- `apps/crm-web/config/healthProxy.test.ts` — `does not let a regex metacharacter in an allowlist path widen the matcher`: five metacharacter cases (`.`, `+`, `(`, `)`, `|`, `$`), each required to match only itself and never a widened variant; plus `keeps the allowlist paths as literal alternatives`.

**The adapter.** `checkHealth(signal: AbortSignal): Promise<HealthResult>` replaces the previous
`createHealthClient` surface. `HealthResult` is discriminated by `kind` over `ready`, `unavailable`,
`timeout`, `network` and `invalid`. The local classification codes are exactly
`WEB_REQUEST_TIMEOUT`, `WEB_NETWORK_ERROR` and `WEB_CONTRACT_INVALID`; the fourth code
`WEB_HEALTH_UNAVAILABLE` of Task 5 no longer exists. The whole check, including the body read, is

`AbortController` that aborts the pending body. A timeout, a transport failure and a contract
violation are closed local paths and carry a client correlation identifier with the `web-` prefix;
a server correlation identifier is carried only by the `unavailable` variant and only when it
matches a conservative display pattern. A malformed server correlation identifier is not displayed
and no server reason or correlation is ever fabricated for a network error.

**The contract boundary.** The success body is accepted only as the documented payload
`{"status":"ready"}`; `{"status":"degraded"}`, a non-JSON body and any other shape are

`reasonToken` and `correlationId` match the canonical schema and their length bounds; the reason
token pattern is the contract pattern `^[A-Z][A-Z0-9_]+$`. Unknown properties of a Problem are
ignored because nothing of the payload is rendered. The rendered output contains the safe message,
the reason token and the correlation identifier only: never the response body, the problem title
or detail, a stack trace, the request URL, a query string or a token.

**The UI.** The home page shows the readiness state of the platform and a `Check again` action. The
state is announced through `role="status"` with `aria-live="polite"`. One check runs when the page

check cancels the pending request, an unmount cancels it as well, and a stale response never
overwrites the state of a newer check. Nothing is written to browser storage, a service worker or a
cookie.

### Task 7 — aggregate gate, clean exact-SHA export and evidence (review pending)

#### The aggregate gate

`scripts/check-plan3.sh` is the Plan 3 public entrypoint that runs the individual public
entrypoints in a fixed order and fails closed on the first failing step. It is the only
Plan 3 script that drives the others; it never implements a check of its own.

```
bash scripts/check-plan3.sh --base-ref <ref> [--with-browser]
```

- `--base-ref <ref>` is **required**. There is no default. A missing or empty value fails
  closed with `PLAN3_ARGUMENT_INVALID` and exit 2, and the value is passed verbatim to
  `scripts/contracts/compatibility.py --base-ref`, which resolves the merge base with `HEAD`
  and never fetches a remote ref.
- `--with-browser` opts in to the browser suite. The suite needs the local Docker stack, so
  the script starts the stack, runs the stack smoke, runs the browser suite and stops the
  stack again. A teardown that fails fails the step with `PLAN3_STACK_TEARDOWN_FAILED`; the
  run never reports success while the stack is still up. Without the flag the step is
  recorded in the summary as `not run`; it is never silently skipped.
- The summary always accounts for **all ten steps**. A step that did not run because an
  earlier step failed is recorded as `not run: an earlier step failed`, in the step table and
  in the command list, so an operator can tell which gates never ran.
- Every condition of the run is reported **exactly once**. Since fix round 4 the aggregate
  records the conditions it detects instead of printing them where they happen: the step that
  detects a condition records it, the step takes its reason token from the condition it
  recorded, and the run reports the recorded conditions once, at the point where it fails.
  Before that change an ordinary failing teardown produced three envelopes for one condition
  — one in the log of the browser step, one as the closed error of the aggregate and one in
  the cleanup. The `INT` and the `TERM` path keep two conditions of their own, the signal and
  the teardown that failed with it, and therefore two envelopes.
- Every closed error path of the aggregate itself produces a reason token and the
  correlation identifier of the run: `PLAN3_ARGUMENT_INVALID`, `PLAN3_PREREQUISITE_MISSING`,
  `PLAN3_TOOLCHAIN_MISMATCH`, `PLAN3_STACK_START_FAILED`, `PLAN3_STACK_TEARDOWN_FAILED`,
  `PLAN3_SOURCE_MUTATED`, `PLAN3_INTERRUPTED`, `PLAN3_TERMINATED` and a failing step. The
  identifier is a UUID generated once per run and printed in the header, so the report of a
  run and the report of its failure carry the same identifier.
- The signal paths are closed error paths too. An `INT` reports `PLAN3_INTERRUPTED` and exits
  130, a `TERM` reports `PLAN3_TERMINATED` and exits 143, and both carry the correlation
  identifier of the run. The exit codes 130 and 143 are the conventional codes of the two
  signals and are unchanged. The envelope is written to the stderr that the aggregate had
  before a step redirected it into its own log, so an interrupted run still reports the
  failure to the operator instead of leaving it in the log of the step that was running. A
  stack that the interrupted run could not stop reports `PLAN3_STACK_TEARDOWN_FAILED` with the
  same identifier, rather than a bare prose warning.
- Prerequisites are checked before the first step: `node` must be the version in
  `.node-version` (24.22.2) and `docker` and `python3` must exist. A missing or mismatched
  prerequisite fails closed with `PLAN3_PREREQUISITE_MISSING` or `PLAN3_TOOLCHAIN_MISMATCH`
  instead of producing a misleading step failure.
- The script never fetches, resets, rebases or rebaselines Git. It has no `git fetch`,
  `git reset`, `git checkout`, `git rebase`, `git commit` or `git pull` anywhere.
- The script never modifies a tracked file. Before and after the run it computes a digest
  over every tracked path of `HEAD`, **over every file of the Git index** (a file that is
  staged but absent from `HEAD` belongs to neither the tracked list of `HEAD` nor the
  untracked list) **and over every untracked, non-ignored file** (content hash, symlink
  target or a `missing` marker) and compares the two. A difference fails the
  run with `PLAN3_SOURCE_MUTATED`. The digest is the aggregate's own proof that no step
  changed the lockfile, the generated SDKs, the canonical contracts or the toolchain inputs.
  If the tracked list cannot be read from Git, the digest falls back to a reduced scope and
  the run says so with an explicit warning instead of pretending to be complete.
- The stack lifecycle is owned by the run from the first attempt to start it. The run
  assumes the stack may be partially up while `dev-up.sh` is still running, so it calls
  `dev-down.sh` after a **failed** start as well, and a teardown that fails on that path
  fails the step with `PLAN3_STACK_TEARDOWN_FAILED` instead of being reduced to a warning.
- An `EXIT`, `INT` or `TERM` trap stops a local stack that this run started, so an
  interrupted run cannot orphan the stack. A teardown that fails on that path is reported
  as the envelope `PLAN3_STACK_TEARDOWN_FAILED` with the correlation identifier, not as a
  bare warning, and it is reported once, next to the envelope of the signal itself. The
  cleanup names the disposition of the run, which the aggregate keeps in `run_state`: "the
  run ended", "the run was interrupted" or "the run was terminated". An ordinary exit is
  described as "the run ended"; the wording of an interrupted run is no longer applied to a
  run that was never interrupted.
- The echoed step output is passed through a defensive redaction of the common secret
  shapes (bearer values, `Authorization` headers and the usual password, secret, token and
  key assignments). The deeper property, that the driven tools never emit a secret, stays
  theirs; the aggregate does not claim more than that.
- The summary prints, per step, the step name, the command, the exit code, the duration in
  seconds and the reason token, followed by the source digest and the overall verdict.

#### Clean exact-SHA export

`tests/Plan3/clean-export.sh` performs the export and the run:

1. The exported commit and the base revision must already exist in the local clone
   (`git cat-file -e <rev>^{commit}`); a revision that the clone does not have fails closed
   with `CONTRACT_BASE_UNAVAILABLE` and never becomes an empty baseline.
2. `git archive <sha>` produces a directory with exactly the tracked content of that commit.
   It has no Git history of its own and no `.local/plan3-tools/`.
3. The export gets a read-only Git object context: a `.git` directory with `HEAD` pointing
   at the exported commit and `objects/info/alternates` pointing at the object store of the
   local clone. The export can therefore resolve the trusted base revision without a fetch
   and cannot create or change any object.
4. The pinned local tool artifacts that are not committed (the oasdiff binary and the
   Corvus.Json.Cli package) are copied into the export and the SHA-256 of both is printed.
   The tooling verifies the same digests itself, so a substituted artifact fails closed.
5. The aggregate runs inside the export.

### Fix round 7 — the scratch cleanup of the Plan 3 harnesses (review pending)

This round changes one mechanism and nothing else: how the scratch directories of this slice
are deleted. No assertion, no printed message, no reason token, no correlation identifier, no
exit code and no order of operations changed. No canonical contract, no backend source, no
container configuration, no stack lifecycle and no CI workflow changed.

**The problem.** Some agent runtimes put a recoverable-delete shim named `rm` on the `PATH`.
On Linux that helper moves its target into the trash of the user (the XDG Trash spec) instead
of unlinking it. The Plan 3 harnesses and the aggregate gate deleted their own scratch trees
with a bare `rm -rf`, so under such a runtime every run **copied** its scratch tree into the
trash of the user instead of freeing the disk: 207 runs had deposited about 55 GB in
`~/.local/share/Trash`, the largest single scratch trees being about 3.7 GB (a NuGet package
cache plus npm-installed SDK tarballs inside a `mktemp -d` directory). A normal developer
machine has no such shim, so the scripts were not broken for developers — but a scratch
directory that a script created itself, minutes ago, must be **unlinked**, not copied into a
trash.

**The change.** The new shared helper `scripts/lib/scratch-cleanup.sh` resolves the rm binary
to an **absolute** path: `/bin/rm` first, then `/usr/bin/rm`, and only a host without both
falls back to the rm of the `PATH`, which is resolved to an absolute path as well. The helper
prints nothing when it is sourced and writes nothing to stdout. Every scratch deletion of the
slice now goes through the resolved binary, with the end-of-options separator so that a
target that starts with a dash cannot be read as an option:

| File | Scratch deletion |
|---|---|
| `scripts/check-plan3.sh` | the log directory of the run |
| `tests/Plan3/aggregate-reporting.sh` | the work directory of the harness and the sandbox of a case |
| `tests/Plan3/ci-environment.sh` | the scratch checkout of the simulation |
| `tests/Plan3/clean-export.sh` | the export directory |
| `tests/Plan3/negative-cases.sh` | the work directory of the harness and the sandbox of a case |
| `tests/ClientConsumers/run.sh` | the temporary directory of the consumer build |

The helper is sourced through `$root`, so the change survives a copy of the checkout into a
sandbox.

**The regression protection is `tests/Plan3/scratch-cleanup.sh`.** It runs the fastest Plan 3
harness (`tests/Plan3/ci-environment.sh`) in a child shell whose `PATH` carries a **fake rm**
first. The fake rm behaves like the recoverable-delete shim: it records that it was called and
it moves its target into the trash of a **controlled** `XDG_DATA_HOME` instead of unlinking
it. The child also runs with a **controlled** `TMPDIR`, so its scratch lands inside the
controlled directories of the harness and the trash of the user is never touched. The harness
asserts that the child exited 0, that the fake rm was never invoked, that the controlled data
home stayed empty and that the controlled `TMPDIR` is empty afterwards. The harness is
self-contained: it resolves the rm binary for its own scratch by itself and does not use the
helper under test, so it can be run against a tree that does not have the helper at all. It
is a case of `tests/Plan3/aggregate-reporting.sh`, which grew from 15 to 16 cases.
