### Task 5 fix round 1 — credential stripping and matcher escaping (review pending)

The independent review of `ffcc7ae` raised one blocking Important finding and one recommended finding, both in the proxy boundary.

**I-1 — the dev proxy relayed the browser's credential headers to the upstream API.** http-proxy copies the incoming request headers into the outgoing request (`outgoing.headers = { ...req.headers }`) and deletes `authorization` only when `options.auth` is set, which the health proxy does not set. A loopback stub therefore received `authorization: Bearer …`, `cookie: session=…` and `x-tenant-id: …` from the browser. The operational endpoints are anonymous by contract, so relaying them would hand a browser session or a tenant selection to the API host the moment the browser holds credentials.

The fix removes the credential-bearing headers at the proxy boundary, in the proxy's own request hook, so it applies to every proxied request:

- `apps/crm-web/config/healthProxy.ts` adds `STRIPPED_PROXY_HEADERS = ['authorization', 'cookie', 'x-tenant-id']` and a `configure` hook on the proxy options that removes them in the `proxyReq` event.
- `authorization` is the `bearerAuth` scheme of the CRM API contract; `cookie` is the browser session; `x-tenant-id` is the canonical tenant context header of the CRM API (`docs/contracts/crm-api.openapi.yaml`, the `TenantContext` parameter). No invented tenant header name was added.
- The list is deliberately small. `Accept`, `Content-Type` and `X-Correlation-Id` are legitimate request headers and are forwarded unchanged, and the regression test asserts that they still arrive.

**M-4 — the proxy matcher was only incidentally regex-safe.** The matcher was built by joining the allowlist paths with `|`, so a future path such as `/health/live.v2` would have produced a matcher that also accepted `/health/liveXv2`. `buildProxyMatcher` now escapes every regular-expression metacharacter of every path, so the "the allowlist and the matcher cannot drift apart" guarantee is structural rather than incidental.

Covering tests:

- `apps/crm-web/config/devServer.test.ts` — `never relays a credential-bearing header to the upstream API`: the real Vite dev server plus a real loopback stub API. The stub now records the headers it received. The request carries `authorization`, `cookie` and `x-tenant-id`; the assertions require the upstream to have received none of them, and to have received `accept` and `x-correlation-id`.
- `apps/crm-web/config/healthProxy.test.ts` — `does not let a regex metacharacter in an allowlist path widen the matcher`: five metacharacter cases (`.`, `+`, `(`, `)`, `|`, `$`), each required to match only itself and never a widened variant; plus `keeps the allowlist paths as literal alternatives`.

### Task 6 — health UI, cancellation and browser behaviour (review pending)

Task 6 delivers the operational health UI, the health adapter with its deadline and
classification, the browser end-to-end suite and the leak scan. The Task 5 review findings that
were carried forward are closed in this round: the fourth local classification code is gone, the
5 second deadline includes the body read, transport failures are classified, the success body is
validated, the credential strip no longer depends on the proxy request hook, the strict-port test
no longer binds the real port 5173 and the declared operations-client dependency is documented.

**The adapter.** `checkHealth(signal: AbortSignal): Promise<HealthResult>` replaces the previous
`createHealthClient` surface. `HealthResult` is discriminated by `kind` over `ready`, `unavailable`,
`timeout`, `network` and `invalid`. The local classification codes are exactly
`WEB_REQUEST_TIMEOUT`, `WEB_NETWORK_ERROR` and `WEB_CONTRACT_INVALID`; the fourth code
`WEB_HEALTH_UNAVAILABLE` of Task 5 no longer exists. The whole check, including the body read, is
bound by one deadline of `HEALTH_DEADLINE_MS = 5000`, implemented with an internal
`AbortController` that aborts the pending body. A timeout, a transport failure and a contract
violation are closed local paths and carry a client correlation identifier with the `web-` prefix;
a server correlation identifier is carried only by the `unavailable` variant and only when it
matches a conservative display pattern. A malformed server correlation identifier is not displayed
and no server reason or correlation is ever fabricated for a network error.

**The contract boundary.** The success body is accepted only as the documented payload
`{"status":"ready"}`; `{"status":"degraded"}`, a non-JSON body and any other shape are
`WEB_CONTRACT_INVALID`. A Problem response is accepted only when `type`, `title`, `status`,
`reasonToken` and `correlationId` match the canonical schema and their length bounds; the reason
token pattern is the contract pattern `^[A-Z][A-Z0-9_]+$`. Unknown properties of a Problem are
ignored because nothing of the payload is rendered. The rendered output contains the safe message,
the reason token and the correlation identifier only: never the response body, the problem title
or detail, a stack trace, the request URL, a query string or a token.

**The UI.** The home page shows the readiness state of the platform and a `Check again` action. The
state is announced through `role="status"` with `aria-live="polite"`. One check runs when the page
mounts and one more per explicit retry; there is no polling and no automatic retry. A repeated
check cancels the pending request, an unmount cancels it as well, and a stale response never
overwrites the state of a newer check. Nothing is written to browser storage, a service worker or a
cookie.

**The proxy credential strip (F-1).** The strip now happens on the incoming request, before the
proxy copies the request headers to the outgoing request, so it applies to every proxied request.
The proxy request hook is not the only mechanism any more: Vite emits that hook only when the
outgoing request carries no `Expect` header, and a request with `Expect: 100-continue` bypassed the
strip entirely. The browser threat model was never affected, because `Expect` is a forbidden header
name for a browser; the control is nevertheless applied to every proxied request now. The
regression test `never relays a credential-bearing header when the request carries an Expect header`
fails without the fix with `expected 'Bearer secret-token' to be undefined`.

**The strict-port test (M-7).** The test binds an ephemeral port on the same host instead of the
real port 5173 and closes the dev server it starts, so it no longer collides with the browser
suite and no longer leaks a server handle.

**The declared dependency (M-9).** `apps/crm-web/README.md` documents that
`@crm-centric/operations-client@0.1.0` is declared but resolved to the generated source
`sdks/typescript/operations/index.ts` by the Vite alias, the TypeScript path mapping and the Vitest
alias; the package's compiled `dist/` output is an uncommitted build artifact. The Playwright suite
runs against the bundle that the dev server built with the same alias.

### Task 6 fix round 1 — enforced deadline, stack provenance, markup scan and correlation fallback (review pending)

The independent review of `fecac28` returned no Critical issue and four findings that are about
enforcement rather than about the behaviour of the implementation: the value of the five second
deadline was asserted by no test, the stack-provenance check of the browser smoke test did not
identify the container of the stack, the two DOM-level safety checks read the visible text only,
and one closed error path carried a reason token but no correlation identifier. All four are closed

**I-1 — the deadline value is now enforced.** `apps/crm-web/src/health/healthClient.test.ts` pins
the literal with `expect(HEALTH_DEADLINE_MS).toBe(5_000)`, and the browser suite now measures the
elapsed time until the deadline fires: the timeout test asserts an elapsed time greater than four
seconds and smaller than nine seconds, so a deadline that is too short and a deadline that is too
long both fail. The unit test proves it: with `HEALTH_DEADLINE_MS` temporarily re-valued to `500`
the suite failed with `AssertionError: expected 500 to be 5000` (1 failed, 53 passed); the constant
was restored to `5_000` afterwards.

**I-2 — the smoke test identifies the API container of the stack.** The check no longer looks at the
published ports of every container. `apps/crm-web/tests/e2e/stackProvenance.ts` resolves the
compose project of the checkout the same way `scripts/local/compose.py` does — the explicit
`LOCAL_STACK_PROJECT` or `crm-local-` plus the first twelve hexadecimal characters of the SHA-256
of the resolved checkout path — and then reads the container of the API service with the compose
labels `com.docker.compose.project` and `com.docker.compose.service=crm-api`. The selection
additionally requires the compose container name `<project>-crm-api-<index>`. A foreign container
that publishes the same port is therefore never the stack. The unit test
`apps/crm-web/tests/e2e/stackProvenance.test.ts` covers the rejection of a foreign container, of
the API container of another compose project and of an empty container list, and the selection of
the container of the stack. RED evidence: with the pre-fix selection the three rejection cases

experiment confirmed it: with the stack stopped and a foreign container

still matched (`docker ps --format '{{.Ports}}'` contains `127.0.0.1:5080->`) while the new check
returned no container of the stack. The experiment and the temporary container were removed
afterwards.

**M-1 — the safety checks read the rendered markup.** The leak scan now scans `page.content()` and
the markup of the application root instead of the visible text, and the browser test asserts on the
markup of the application root and on the whole document. RED evidence: with the raw problem
payload rendered into a `title` attribute of the status region, the previous text-only scan
reported `no sentinel, secret, credential or local metadata leak` and exited 0, while the new scan

**M-2 — every closed error path carries a correlation identifier.** The `unavailable` variant now
always carries a client correlation identifier. When the server sent a usable correlation
identifier it is shown as `Server correlation:`; when the server correlation identifier is
malformed, the client correlation identifier is shown instead, so a server identifier is never
fabricated and every closed path carries a reason token and a correlation. The adapter test and the
component test cover the malformed server correlation identifier.

directory and pointing `LD_LIBRARY_PATH` at it is an equivalent local workaround. The step is a local
prerequisite of the browser only and was not added to the build, the test scripts or any
continuous integration path of the repository; no machine-specific path is part of the code or the
configuration.
