## Concrete review artifact

[Proposed JSON](2026-11-13-mvp-exact-finding-policy.proposed.json) enumerates exactly the original 64 opaque finding IDs, each with path, structural field, line, rule, multiplicity, source kind and digest of the complete metadata document. Its context fixes the original reviewed candidate `b1c86f931fdc0a3ab95ea2243c95b35f29637851`, scanner version, scanner executable digest and scanner configuration digest. Every decision is `pending`, owner empty, expiry unset. It contains neither raw matched values nor credentials.

`scripts/ci/finding_adjudication.py:adjudicate_mvp` consumes policy bytes in memory. No workflow, runner, scanner configuration, scanner verdict or ignore file calls it. Default/missing, malformed, duplicate-key, unknown-field, stale-context and duplicate-ID policies block. The adapter preserves all native records privately with bounded reason tokens and correlation IDs. Successful MVP records also carry `verification_basis`; reviewed JAR snapshots use `CI_METADATA_SNAPSHOT_REVIEWED` so evidence distinguishes manual snapshot review from source recomputation. Do not serialize returned native records into public reports.

A future authorized activation would require a trusted maintainer to review the exact code and per-ID policy, assign an accountable owner and expiry, and approve only the intended IDs. `approved` inside candidate-owned JSON is a declaration interpreted by this adapter, **not proof of authorization**. A malicious candidate can change code, policy or snapshot mappings. This approach suits a workflow in which a trusted maintainer reviews those changes before relying on the result; it provides no independent enforcement against candidate authors. The existing independent capability kernel remains available as a separate future hardening seam. No verifier service, signature, attestation or protected-check provisioning is required to review this MVP option.

The caller must supply documents and identity from the candidate actually scanned, including executable/configuration digests; the Python interface cannot prove that acquisition. The full metadata document digest binds the reviewed bytes, beyond the redacted record fingerprint, so changing a selected value cannot reuse its ID. Contract source-byte recomputation, whole selected member matching, strict JSON parsing and multiplicity checks still apply. For JARs the explicit `reviewed-jar-snapshot` basis substitutes the exact reviewed metadata snapshot for runtime source-byte recomputation; this tradeoff requires user approval. New findings and all history findings remain blocked, including records whose redacted fingerprint resembles a current-tree record. No broad rule/path/hex ignore exists.

The sixty diagnostic JAR entries cannot be recomputed on CI from available repository inputs. Retained local build bytes supported the earlier manual review; they establish neither upstream authenticity nor repeatable CI acquisition. The proposed `reviewed-jar-snapshot` decision basis allows an explicit, narrowly bound one-candidate review to rely on that earlier local-byte comparison without downloading JARs at runtime. It checks the exact metadata-document digest and native record identity, structural member, location and multiplicity. Changed values alter the document digest and block even if their redacted ID stays unchanged. This does not recompute JAR hashes during CI, prove upstream authenticity, or independently authenticate the review. The proposed configuration records this basis for each of the sixty entries, but every decision remains pending. Trusted maintainer review of code and policy plus explicit user approval is required before activation.
