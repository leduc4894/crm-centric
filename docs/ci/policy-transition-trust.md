# Policy transition trust proposal

Status: local boundary and real semantic runner implemented; operational transitions **BLOCKED**, provisioning **OPEN**. Governed by the [trust spec](../superpowers/specs/2026-11-11-wave-0-plan-4-ci-wave-exit-design.md#revision-và-compatibility-trust).

No independent required workflow, signing authority, key ownership, or repository ruleset has been provisioned or verified. A PR approval file is not authority. The current compatibility CLI still rejects all policy changes and has no approval/key CLI or environment option.

An owner must separately approve and provision verifier source pinned outside candidate control (or explicitly base-controlled), signing service/key ownership and rotation/revocation, attestation retrieval, required-check enforcement and immutable evaluator images. Do not give signing credentials to candidate jobs. Installing this module in a candidate workflow does not establish trust.

`verify_transition(attestation, trusted_key, revision, old_hashes, new_hashes)` requires the externally supplied capability's `verify(canonical_payload_bytes, signature)` to return literal True. Canonical JSON uses UTF-8, sorted keys, compact separators, no non-finite numbers. The adapter must implement a reviewed signing algorithm and independently pin the public trust anchor. No production signature algorithm/key backend is provisioned here; tests use only a synthetic HMAC fixture. No verifier is discovered from PR files, environment variables or candidate modules.

The same trusted adapter must supply old/new policy and base/candidate contract snapshots from validated immutable Git objects as tuples of `(relative_path, bytes)`, actual candidate tree and independently reviewed merge method. Attestation binds exact old/new policy hashes, file scope, base/head/candidate SHA, tree, event, merge method, identity, ADR, consumer evidence references, reviewer and expiry. Evidence validity is the signing authority's responsibility, not inferred from nonempty PR strings. Unknown fields and adapter failures close the gate with safe reason token/correlation ID.

First main push needs a push-specific attestation binding `before` as base and actual resulting commit/tree with reviewed merge method. PR approval cannot automatically authorize push. Changed squash/rebase output or advanced base requires new approval. Rollback needs a separately signed reverse transition.

`policy_identity_preflight` separates identity from semantic checks. Default Plan 3 callers supply no transition and fail closed on changed hashes. A trusted coordinator may provide only an exact verified revision/hash transition. Python data objects are an in-process interface, not a sandbox or unforgeable credential.

`evaluate_transition` belongs in a separate **unprivileged** phase. Independently pinned runners evaluate old and new immutable policy snapshots using identical base/candidate contract bytes. Both must report compatible. Either breaking/security/schema/SDK finding or tool failure fails the combined result, retaining both normalized result tokens and attestation identity. Never execute candidate evaluators in the privileged verifier. The signature-verification function imports no candidate evaluator, executes no semantic subprocess, and performs no baseline replacement or contract rewriting. The separate Git adapter uses only read-only object queries.

A local `GitSnapshotCapability.from_git` adapter now reads exact base/candidate Git blobs and the actual candidate tree using read-only commands with replacement objects and lazy fetch disabled. It ignores dirty worktree content and rejects missing/non-blob/symlink inputs. The trusted caller must supply the complete independently reviewed policy-path inventory, the revision already proved by `resolve_event`, signature verifier, and reviewed merge method. This adapter does not establish independent workflow provenance by itself.

Result evidence now retains old/new policy hashes and base/candidate contract hashes on both compatible and incompatible paths.

`Plan3SnapshotEvaluator` now implements local execution of the real semantic toolchain. It materializes exact policy and contract byte snapshots in temporary directories, verifies the selected oasdiff checksum, and starts `semantic_worker.py` in a fresh process. The worker imports the **selected snapshot's** semantic module and SDK checker, uses that policy's pinned offline npm dependencies and container/tool configuration, and runs wire/security/schema checks, real SDK generation, public-surface comparison and historical TypeScript/.NET consumer compilation. The baseline generator and consumer source stay fixed to the reviewed old policy while each evaluation uses the selected candidate generator policy. Both policies receive identical actual event-base/candidate contracts; the event base is supplied explicitly, never recomputed or replaced. Policies predating the extracted semantic API require separately reviewed bootstrap and fail closed; they are not rewritten on the fly.

The worker is an execution boundary, not an OS sandbox. The production coordinator must schedule it in a separate disposable unprivileged job with no signing credentials or repository secrets; candidate policy scripts and Docker tooling must never execute in the verifier job. Local tests execute only test-owned, reviewed snapshot code. The worker receives an environment allowlist, captures diagnostics, uses finite timeouts, and does not upload raw output. The existing compatibility CLI still executes its unchanged identity preflight and exposes no passing transition option.

Still OPEN: approved external signing adapter and independently provisioned required workflow, policy inventory, job isolation and attestation transport. Those remote trust controls remain unprovisioned. Local runners and tests do not establish independent enforcement. Until provisioning exists the normal gate has no passing transition route. No remote changes were authorized or performed.
