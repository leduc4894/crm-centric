# Proposal: exact-candidate reviewed schema compatibility

Status: **user approved the design direction for planning; this document is not an exact-candidate review approval, implementation, waiver or CI result**. No policy, CLI flag, gate or input is changed by this document. The present candidate remains uncommitted and `SCHEMA_COMPATIBILITY_REVIEW_REQUIRED` is the actual result against base `60136693c24886f8fa65826185e8a6b80f3f45d8`. Security and aggregate remain FAIL/deferred, Wave 2/P0 OPEN. No credential/provider/receiver enforcement or P0 acceptance is established.

## Existing behavior and limits

- `scripts/contracts/compatibility.py` computes `baseSha` as `merge-base HEAD <base-ref>` and `targetSha` as the resolved **base-ref**, not the candidate HEAD. It hashes all OpenAPI/JSON Schema inputs and local reference closures; any new schema is `schema-review-required` except a narrow historical contact review. On this branch the two new challenge schemas trigger that early return, so the actual later security, oasdiff and SDK checks were not run by that invocation.
- Existing `reviewed_contact_change` requires opt-in, a fixed base, expiry, exact complete input digests and evidence-file hashes. The prior review is candidate-owned (`independentVerification: false`), not a signed independent attestation. Policy-source preflight is separately checked; its historical exception is narrow. `CONTRACT_BREAKING_REVIEWED` returns exit 0 today, so its interpretation and mandatory CI effects are significant.
- Important implementation detail: the current oasdiff block returns `CONTRACT_BREAKING` immediately on findings. A new reviewed path must not be imagined as already doing end-to-end diff review merely because the earlier contact flags exist. Uncommitted work cannot be identified as an immutable candidate just by quoting `targetSha` in the existing output.

## Binding and evidence, to be designed before code

1. Establish the true event base `B` as the actual CI merge base; resolve an immutable candidate commit/tree `C` separately from the CLI's existing `targetSha`. The current `6013669` is a local comparison base, not evidence that every eventual CI event has that base. Reject dirty candidate inputs, wrong commit/tree, stale attestation, unreachable or ambiguous base, and drift after review. Review `C`; do not include a self-referential review record in the tree whose hash the record signs. A detached, separately controlled review artifact or later review commit can refer to `C` and its tree hash. Existing `RevisionContext` has no event kind or integration method; a protected coordinator must independently authenticate event provenance and wrap it, failing closed if it cannot.
2. Review record has a strict versioned schema and includes: `B` full SHA; `C` full commit SHA and tree hash; exact complete sorted path → SHA-256 maps for **both** base and candidate OpenAPI/JSON Schema files and all local reference closure; changed-schema identities and review findings; ADR-023 and migration/rollback digest; SDK generator, policy/tool configuration and exact current generated SDK/consumer fixture digests; test commands/results and their candidate/environment; issue/review identities, approval scope and UTC expiration. Exact content, byte encoding, normalization and signing canonicalization must be specified. Reject duplicate paths/JSON properties, duplicate approvals, extra/missing paths, symlinks in any component, path traversal, nonlocal references, malformed or non-SHA-256 values, unknown record fields, mismatched digests and expired/revoked evidence.
3. A trusted authorization mechanism must bind reviewers and the record outside the candidate's control, e.g. protected CI environment or verifiable signed artifact with pinned key/issuer and authorized roles. A file that candidate authors can simply edit is evidence of a self-declared review, not independent approval. Require explicit named scope for schema additions, each breaking API/SDK finding, mTLS/token security changes, ADR and migration; one approval does not automatically cover additional findings or runtime security. User approval of architecture and deferred security do not constitute this artifact. Protect keys and avoid placing credentials in repo/logs. If this authority cannot be established, leave FAIL; don't mark a candidate-only record independent.
4. Compare the fixed actual policy/toolchain against both base and candidate. A policy-changing PR requires its own authorized, exact-digest review and baseline/target evaluation before it can attest to a contract change; it cannot authorize itself. Preserve raw old and new policy verdicts, including an early schema-review-required result with explicit incomplete coverage; never rewrite a historical evaluator or imply that it ran the later checks. A separately trusted, independently pinned full-gate collector must run every required check on the same immutable snapshots and report each outcome. Use a separately trusted evaluator or protected policy revision. Do not trust candidate changes to checkers or tests as proof of those same changes. Define how local drafts and CI compare to an immutable baseline; no wildcard, "current HEAD", date-free or broad allowlist.

## Event identity and detached approval

A protected coordinator must authenticate the event source independently; no current source file proves that infrastructure exists. The verified wrapper carries `RevisionContext`, authenticated event kind/provenance and separate integration method. `RevisionContext` itself carries neither event kind nor method. For pull requests, `base_sha` is the event PR base, `head_sha` the PR head, `candidate_sha = merge_sha =` run-bound `GITHUB_SHA`; checkout must match and candidate parents must be exactly `[base_sha, head_sha]`, with merge-base equal to base. The synthetic CI merge is not evidence of eventual merge, squash or rebase strategy; for reviewed PR eligibility that strategy must be separately authenticated through trusted approval, never inferred from parents. For push, event `before` is `base_sha`, `after` is `head_sha = candidate_sha`, `merge_sha` is null, `forced` is exactly false, checkout equals after and merge-base equals before. The push integration method is null/not applicable, not inferred from a PR strategy; the current push path does not separately validate `GITHUB_SHA`.

A reviewer issues a detached attestation only after the exact event candidate commit and tree are immutable and the trusted event source proves them. The record binds event, base, head, candidate, tree and applicable strategy; changed base/head or a regenerated PR synthetic merge invalidates it. Missing trusted event provenance, unproved strategy, absent authority, invalid commit/tree or mismatch fails closed. Local fixtures are not evidence that the protected event source or signer exists.

## Evaluation and results

- Keep unmodified raw old/new policy verdicts with explicit coverage. Separately, a trusted independently version-pinned full-gate collector validates all schemas, references and hashes, then runs *all* security analysis, pinned oasdiff, SDK surface and old/new independent consumers on identical immutable snapshots even if a raw evaluator returned early for a schema change or breaking diff. Record complete machine-readable findings and tool errors; fail closed on missing tools, execution errors, skipped required tests, unexpected findings or absence of required evidence. A review record must match every discovered finding and no broader permission. The current early return must be refactored carefully; do not turn off checks or accept errors as reviewed.
- A security change such as new mTLS gate has separate review scope; exact schema approval alone cannot authorize it. Binding `C` and all input/evidence digests prevents reuse for a later changed contract but does not establish real IdP, receiver, provider or deployment safety. Independent old/new consumer tests must demonstrate both intended break and migration; actual deployed consumers and rollout must be inventoried separately.
- If and only if every policy, diff, schema, security and test condition is met, emit `CONTRACT_BREAKING_REVIEWED`, classification `reviewed-breaking`, with base/candidate/evidence digests, scopes, reviewer identity/expiry and individual outcomes. Never emit `compatible` for this change. Decide explicitly whether this reason may return exit 0 in the existing required CI job: current code allows that, so any continuation must be approved as a policy change with independent review and must not alter unrelated mandatory gates. If deployment gate requires independent security clearance or real acceptance evidence, keep it failing separately. Missing/incomplete approval must retain nonzero gate status.
- Candidate current state has no exact approved artifact, review identity authority, policy-change review or completed semantic gates. Do **not** implement an exception against placeholder digests or add a flag that marks current candidate reviewed; keep `SCHEMA_COMPATIBILITY_REVIEW_REQUIRED`.

## RED → GREEN test matrix for a future implementation

Tests exercise the real gate/evaluator on isolated git repos and fixed, synthetic trusted review artifacts, as well as the CLI's pinned tools; synthetic signing keys are expressly test-only. No production reviewer identities or credentials are embedded. Required minimum cases:

| Case | Expected result |
| --- | --- |
| Correct base, immutable candidate/tree, exact complete files/evidence, authorized nonexpired record, all real checks and reviewed breaking findings | `reviewed-breaking`, never `compatible`; exact individual outcomes visible. |
| One-byte mutation of each schema/OpenAPI/reference, ADR, generator, policy/tool, generated SDK or consumer evidence | Reject review; nonzero; no stale authorization reuse. |
| Add/remove/rename an input; replace any file or parent with symlink; duplicate record field/path, traversal/nonlocal ref | Reject, nonzero; no partial list comparison. |
| Wrong actual merge base, mismatched target ref, dirty tree, modified candidate post-review, wrong tree or candidate SHA, old/expired/revoked review | Reject, nonzero. Include the existing `targetSha` ambiguity. |
| Missing/forged signature, wrong issuer/key/reviewer role, wrong scope, review signed before a new security finding | Reject, nonzero; record explicitly says not independently verified if independent authority unavailable. |
| New or changed mTLS/token/security finding without matching separate security review | `security-review-required` or stricter nonzero, even with schema review. |
| oasdiff unexpected finding/error, invalid schema/ref, SDK diff beyond reviewed scope, consumer failure, required test skipped/tool unavailable | Nonzero with original reason/correlation; never reviewed-breaking. |
| Correctly recorded intentional breaking diff | Test old consumer rejects new receipt, new consumer validates real contract, migrations and exact evidence; `reviewed-breaking` only after independent review. |
| Review/policy file self-modification, claimed approval by candidate, concurrent rewrite, same record with altered candidate | Fail closed; compare immutable snapshot bytes rather than rereading a mutable working tree. |
| Audit/review artifact unavailable or ambiguous timestamps | Fail closed; no silent fallback or claim of P0 acceptance. |

Implementation would require its own plan, threat model and TDD review before applying policy; test on synthetic fixtures first. Do not add any real review hash until the candidate, independent review and authorization exist. Full suite and required CI remain enabled.
