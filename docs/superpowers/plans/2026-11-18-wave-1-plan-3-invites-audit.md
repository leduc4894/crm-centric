# Wave 1 Plan 3 — Invitations and Audit Implementation Plan

> **For agentic workers:** Execute sequentially with `superpowers:executing-plans` and one coding agent. Follow RED → GREEN, preserve existing changes, and make small reviewable commits.

**Goal:** Let an authorized tenant administrator issue and revoke invitations, and let the intended verified staff identity accept exactly once, with durable transactional audit and tenant-scoped audit access.

**Architecture:** Invite management uses the existing verified tenant transaction and `team.manage`; acceptance resolves tenant from a SHA-256 hash of a high-entropy bearer token and checks a verified email and staff binding. PostgreSQL serializes acceptance and membership changes using the existing tenant advisory lock, rechecks all state under lock, and commits membership, invite state and audit atomically. Audit reads use the same verified staff and tenant boundary.

**Tech stack:** .NET 10 / ASP.NET Core, PostgreSQL / EF Core / Npgsql, xUnit, Testcontainers; existing pinned dependencies and OpenAPI.

**Spec:** [P0 access and state](../../architecture/07-P0-ACCESS-AND-STATE.md), [Wave 1 design](../specs/2026-11-15-wave-1-identity-tenancy-design.md), [delivery map](2026-11-15-wave-1-delivery.md), [OpenAPI](../../contracts/crm-api.openapi.yaml), [Plan 2 merge handoff](../../handoff/2026-11-18-wave-1-plan-2-merge-handoff.md).

- Public operations in this plan: `GET/POST /api/v1/invites`, `DELETE /api/v1/invites/{id}`, `POST /api/v1/invites/accept`, `GET /api/v1/audit`. Existing schemas and statuses are authoritative. Breaking contract changes require ADR, migration and consumer tests; this plan does not authorize one.
- Existing staff binding is an explicit operator-verified `(issuer,subject)` record, not a token role claim. Invitation acceptance requires the account to be authenticated, have an active verified staff binding, and present a verified matching email; an operator must establish the binding through the existing controlled workflow. This prevents an invited integration-service identity from acquiring staff access; acceptance does not create or reactivate the binding, link a CRM contact, or grant extra scopes.
- Creation returns a token once over TLS for manual transfer; no email provider, browser login or frontend is included. Persist only SHA-256 digest of a cryptographically random token, never token or digest in audit/logs/list/URLs. Use 32 random bytes encoded canonical unpadded base64url (43 characters); decode strictly on accept and use SHA-256 over those bytes. Reject noncanonical or incorrect-length tokens uniformly without leaking information.
- The token's tenant is resolved server-side, not from `X-Tenant-Id` or body. Include no tenant header on accept; reject a supplied header with 400 `REQUEST_INVALID` to avoid ambiguity. Accept only one `email` claim and one boolean-typed `email_verified=true` claim from the already verified access token, not an ID token, user-supplied body or email-based identity linkage. Document required IdP mapping; missing, duplicated, unverified or malformed claims fail closed. Test JSON boolean vs string `"true"` by inspecting claim value types from the real JWT handler and validate original claim types if needed.
- Email comparison uses a shared validator for invite and token claims: ASCII mailbox/domain only, no whitespace or control characters, max 320 characters; preserve local-part case, lowercase ASCII domain invariantly, reject invalid syntax. Do not apply provider aliases, dot folding or Unicode normalization. Store original email for `Invite` response and normalized value for matching; both are PII and must not be logged/audited. This deliberately conservative equivalence must be documented for operators.
- Every tenant query/mutation uses validated context and tenant predicate; token-hash bootstrap uses a narrowly scoped fixed-search-path definer function, with PUBLIC revoked, that exposes only candidate tenant ID for one exact hash. It does not authenticate database caller. API app credential compromise permits forged SQL parameters: do not claim RLS or SQL functions defend against arbitrary SQL with that credential. No application credentials in logs.

## Concurrency and state

- Invite status is `pending`, `accepted`, `revoked` or computed `expired` when pending and database time >= `expires_at`; expire at 24 hours from the database timestamp recorded when the invite is created. Use PostgreSQL `clock_timestamp()` for final expiry check after waiting on locks; `now()` is transaction-start time and cannot establish correctness across lock waits. A revoke never changes accepted/expired state; an invalid transition returns 409 `INVITE_STATE_CONFLICT`, while missing/cross-tenant ID returns 404. Revoke pending is 204, no body.
- `accept`: hash lookup is only a hint; begin transaction, acquire exactly `pg_advisory_xact_lock(hashtextextended('crm.membership:' || tenant::text,0))`, lock tenant and invite row, lock verified staff binding, then recheck digest, tenant active, expiry, invite status and matching email. No raw token is passed to DB. Atomically insert active membership with invited role and version 1, consume invite, and write audit. For an existing `(tenant,issuer,subject)` membership, return 409 `MEMBERSHIP_EXISTS`, leave invite pending and never alter role/status or reactivate it. Existing owner is never modified. The unique membership constraint remains the final race guard.
- All membership writes use the same tenant advisory lock. Revoke uses the same per-tenant lock before tenant/actor/invite row locks; accept and revoke recheck state under lock. On deadlock/serialization failure rollback, retry entire transaction at most twice only before commit; after ambiguous commit do not retry and do not claim the invite was unused. Test both winner orderings and repeated accepts on real PostgreSQL. No acceptance succeeds after revoke commits, expiration, or staff-binding revocation wins the lock.
- Every real create/revoke/accept appends one bounded redacted `audit.entries` row in the same transaction; no raw email/token/hash. Failure of audit rolls back all changes. Migration expands the existing audit action check to `invite.created`, `invite.revoked`, `invite.accepted`; keep existing actions and existing audit records. No direct app-role audit writes, updates or deletes. Audit retrieval exposes only tenant-scoped entries with `audit.read`, and excludes separate platform-level `audit.staff_binding_changes`.

## Review focus

1. Verified email claim absence, duplicate/forged claims, false/string boolean and service identity: fail before any membership is created (Tasks 1, 3).
2. Concurrent double accept, accept vs revoke, expiration while blocked, existing membership and revoked staff: at most one state change and no escalation (Task 3).
3. Token in logs, URL/query, errors, database, audit, list, traces or dump of request body: only create response contains raw token; test each observable surface (Tasks 1–3).
4. Cross-tenant cursor, direct SQL privileges, missing context and connection pool reuse: no tenant or audit leakage (Tasks 1–4).
5. Failed audit, backend loss, retry, migration rollback and existing Plan 2 gates: no partial state and no unsupported success claim (Tasks 1, 3, 5).
